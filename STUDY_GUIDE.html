1 How a User Logs In (Passport.js)

When a user submits the login form, Express hands the request to passport.authenticate('local'). Passport's LocalStrategy then runs your custom verification callback. 

// ── Login request flow ──────────────────────────────
Browser  →  POST /log-in  →  passport.authenticate('local')
                                 ↓
                           LocalStrategy callback
                           1. findUserByEmail(email)
                           2. bcrypt.compare(password, hash)
                           3. done(null, user)  ← success
                                 ↓
                           passport.serializeUser  →  stores user.id in session
                                 ↓
                           req.session.passport = { user: 1 }  ← saved to DB

On every subsequent request the reverse happens:

Browser sends cookie  →  express-session reads session from DB
                      →  passport.deserializeUser(id)
                      →  findUserById(id)
                      →  req.user = { id, email, is_member, is_admin, ... }
Why two steps? serializeUser decides what to store in the session (just the id, not the whole user object). deserializeUser uses that id to reload the full user from the DB on every request. This keeps sessions small and user data always fresh.

Key files: config/passport.js (LocalStrategy) · app.js (middleware registration)

2 Passwords with bcrypt

Passwords are never stored as plain text. bcrypt produces an irreversible hash; even if the database is leaked, passwords remain protected. 

// ── Sign-up: hash before storing ───────────────────
const hashedPassword = await bcrypt.hash(password, 10);
// saltRounds = 10  →  2^10 = 1024 hashing iterations

// ── Log-in: compare plain text vs stored hash ──────
const match = await bcrypt.compare(plainPassword, hashedPassword);
// Returns true/false. NEVER compare plain strings!
Salt rounds explained A salt is random data prepended to the password before hashing so two identical passwords produce different hashes. saltRounds = 10 is the CPU cost factor — higher = slower to brute-force, but also slower to hash on login. 10 is a commonly accepted default.
Common mistake Never use === to compare passwords. Always use bcrypt.compare() — it handles timing-safe comparison and automatic salt extraction from the stored hash.

3 Sessions

HTTP is stateless — each request knows nothing about previous ones. Sessions fix this by keeping server-side state tied to a browser cookie. 

1. User logs in  →  session created  →  session ID sent as cookie
2. Next request  →  browser sends cookie  →  server looks up session
3. Session row in DB:
   { sid: "abc123", sess: { passport: { user: 42 } }, expire: "..." }

connect-pg-simple stores sessions in a session table (auto-created). You can inspect it live: 

SELECT * FROM session;  -- run in psql to see active sessions
Session vs JWT This project uses server-side sessions — state lives in PostgreSQL. An alternative pattern (JWTs) stores state in a signed token on the client. Sessions are simpler to invalidate (just delete the DB row) but require DB reads per request.

4 Authorization Levels

The app has four distinct permission levels, checked at both the route level (middleware) and the view level (EJS conditionals).

User State See Messages See Author & Date Delete Messages
Guest (not logged in) ✅ ❌ ❌
Logged-in, no membership ✅ ❌ ❌
Member (is_member = true) ✅ ✅ ❌
Admin (is_admin = true) ✅ ✅ ✅

This is enforced in the view template:

<!-- views/index.ejs ──────────────────────────────── -->
<% if (user && (user.is_member || user.is_admin)) { %>
  <p>By <%= msg.first_name %> <%= msg.last_name %></p>
  <p><%= msg.created_at %></p>
<% } %>

<% if (user && user.is_admin) { %>
  <form action="/delete/<%= msg.id %>" method="POST">
    <button>Delete</button>
  </form>
<% } %>

5 Middleware Pattern

Express middleware is a function with the signature (req, res, next). Calling next() passes control downstream; not calling it stops the chain. 

// middleware/auth.js ───────────────────────────────────
function requireLogin(req, res, next) {
  if (req.isAuthenticated()) return next(); // passport adds this method
  res.redirect('/log-in');
}

function requireAdmin(req, res, next) {
  if (req.user && req.user.is_admin) return next();
  res.status(403).send('Forbidden');
}

// Usage in a route file:
router.post('/delete/:id', requireLogin, requireAdmin, async (req, res) => {
  // Only runs if both guards pass
  await deleteMessage(req.params.id);
  res.redirect('/');
});
Middleware chain You can stack as many middleware functions as you want in a single route definition. Express runs them left-to-right — each must call next() or send a response.

6 Form Validation

express-validator lets you attach validation rules as middleware, then collect all errors at once — giving users friendly feedback instead of crashing mid-handler. 

// routes/authRoutes.js ────────────────────────────────
router.post('/sign-up', [
  body('email').isEmail().normalizeEmail(),
  body('firstName').trim().notEmpty(),
  body('password').isLength({ min: 6 }),

  // Custom validator: passwords must match
  body('confirmPassword').custom((val, { req }) => {
    if (val !== req.body.password)
      throw new Error('Passwords do not match.');
    return true;
  }),
], async (req, res) => {
  const errors = validationResult(req); // collect all failures
  if (!errors.isEmpty())
    return res.render('sign-up', { errors: errors.array() });
  // ✅ Safe to proceed — data is validated
  const hash = await bcrypt.hash(req.body.password, 10);
  await createUser({ ...req.body, password: hash });
  res.redirect('/log-in');
});
Why validate server-side? Client-side validation (HTML5 required, JS) can be bypassed by anyone who opens DevTools. Server-side validation is the real gate — always do both.

7 Project Structure

app.js ← Express app entry point, middleware registration config/ passport.js ← LocalStrategy definition (verify callback) db/ pool.js ← pg connection pool (reused across queries) queries.js ← all SQL queries — no ORM, raw SQL schema.sql ← CREATE TABLE statements (users, messages, session) middleware/ auth.js ← requireLogin, requireAdmin guard functions routes/ authRoutes.js ← GET/POST /sign-up, /log-in, /log-out memberRoutes.js ← GET/POST /join (membership passcode) messageRoutes.js ← GET /, POST /new-message, POST /delete/:id views/ index.ejs ← home page — conditional author visibility sign-up.ejs log-in.ejs join.ejs new-message.ejs partials/ nav.ejs ← shared navigation (login/logout link)

8 Things to Try

  • 1 Sign up as a regular user and post a message. Notice the home page hides the author name.
  • 2 Enter the membership passcode on /join. Reload the home page — the author name and date now appear.
  • 3 Sign up a second user with the Admin checkbox checked. Log in and verify the Delete button appears on messages.
  • 4 While logged out, navigate directly to /new-message. Confirm you are redirected to /log-in.
  • 5 Open psql and run SELECT * FROM session; to see the raw session data stored by connect-pg-simple.
  • 6 Add console.log(req.user) inside any route handler to inspect the full deserialized user object on each request.
  • 7 Delete a session row from the DB directly and try refreshing — notice you get logged out even though the browser still has the cookie.
